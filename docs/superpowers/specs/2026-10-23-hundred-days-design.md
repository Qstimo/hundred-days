# «100 дней до» — дизайн

Дата: 2026-10-23
Состояние: согласован

## 1. Зачем

Личный трекер с ограниченным сроком. Каждый день открывается страница
сегодняшнего дня и заполняется: что сделано, сколько времени на это ушло,
во сколько лёг и встал, что планировал. Поверх ежедневных отметок считается
прогресс навыков в поинтах — так видно не только «не пропустил», но и
«сколько пути пройдено».

Единица учёта — **день**. Не задача и не проект: приложение отвечает на вопрос
«что я сделал за этот день» и «сколько успел за срок».

Приложение самостоятельное. С системой CAIRN его не связывает ничто, кроме
машины, на которой оба стека стоят, и реверс-прокси CAIRN, через который на
последнем шаге пойдёт поддомен.

## 2. Имя

Код и репозиторий — `hundred-days` (`Qstimo/hundred-days`), каталог
`~/Рабочий стол/MyMVP/hundred-days`. Название в интерфейсе — «100 дней до».

## 3. Модель данных

### 3.1. Настройки

`settings` — одна строка на пользователя:

| Поле | Смысл |
| --- | --- |
| `period_title` | заголовок периода, например «100 дней до запуска» |
| `period_start` | дата начала |
| `period_days` | длительность, по умолчанию 100 |
| `sleep_enabled` | показывать ли блок сна |

«Осталось N дней» вычисляется из `period_start` и `period_days`, не хранится.
Хранимое число разошлось бы с календарём на следующий же день.

### 3.2. Навыки

`skills` — RPG-цель: название, цель в поинтах (`target_points`), подпись
единицы (`unit_label`, например «занятие»), порядок, отметка архивации.

Прогресс навыка вычисляется суммой поинтов записей его трекеров. Не хранится:
хранимая сумма разъехалась бы с записями при любой правке истории, а правка
истории разрешена (см. 3.4).

### 3.3. Трекеры

`trackers` — то, что отмечается ежедневно:

| Поле | Смысл |
| --- | --- |
| `title` | название |
| `mode` | `check` — только галочка; `check_hours` — галочка и часы |
| `points_rule` | `per_check` — поинты за выполнение; `per_hour` — за час |
| `points_value` | сколько поинтов даёт выполнение или час |
| `skill_id` | навык, который трекер питает; необязателен |
| `weekly_target` | «N раз в неделю», 1…7 |

Один навык питается несколькими трекерами: «английский уровня B» набирается
и занятиями, и фильмами, и чтением, у каждого своя цена в поинтах. Трекер без
навыка — обычная привычка без прогрессии.

**Инвариант.** `points_rule = per_hour` допустим только при
`mode = check_hours`. Выражен `CHECK` в базе и проверкой в API: иначе правило
считало бы поинты от поля, которого у трекера нет, и получало бы ноль при
каждом выполнении.

### 3.4. Записи

`entries` — выполнение трекера в конкретный день:

| Поле | Смысл |
| --- | --- |
| `tracker_id`, `entry_date` | `UNIQUE(tracker_id, entry_date)` |
| `hours` | часы, только у `check_hours` |
| `points_awarded` | поинты, зафиксированные при записи |

Существование строки и есть «сделано». Снятие галочки удаляет строку —
отдельного значения «не сделано» нет, как нет строки выдачи для уровня «нет»
в CAIRN.

**Инвариант.** Поинты фиксируются в строке записи, а не считаются на лету по
текущей цене трекера. Иначе правка `points_value` переписала бы весь
накопленный прогресс навыка задним числом, и «забрано 240 из 300» менялось бы
от изменения настройки, а не от сделанной работы.

Любой день открыт для записи и правки, без ограничения по давности.

### 3.5. Сон

`sleep_logs` — одна строка на дату:

| Поле | Смысл |
| --- | --- |
| `log_date` | дата подъёма — день, к которому относится сон |
| `went_to_bed_at` | во сколько лёг |
| `woke_up_at` | во сколько встал |
| `quality` | самооценка 1…5 |

Все три значения необязательны: блок опциональный, и заполнить только время
подъёма — нормально.

Длительность вычисляется, не хранится. Переход через полночь учитывается: если
`woke_up_at <= went_to_bed_at`, к подъёму прибавляются сутки. Лёг в 23:40,
встал в 7:10 — семь с половиной часов, а не минус шестнадцать.

### 3.6. Планы на день

`day_plans` — пункт плана: дата, текст, отметка закрытия (`done_at`), порядок,
`carried_from_id` — ссылка на пункт-источник при переносе.

Планы принадлежат дате и сами не переезжают. Незакрытые переносятся кнопкой
«Подтянуть незакрытые со вчера»: она копирует их в сегодня, оставляя в
исходном дне след того, что тогда планировалось и не вышло. Автоматический
перенос размыл бы историю дня, а она здесь и есть содержание.

### 3.7. Пользователь

`users` — логин, хеш пароля (argon2id), имя.
`sessions` — идентификатор, пользователь, срок.

Аккаунт один, регистрации нет: он создаётся CLI-командой на сервере. Но
`user_id` стоит в каждой таблице с первого дня, и **каждая функция доступа к
данным принимает `user_id` в сигнатуре** — проверка на уровне выборки, а не в
хендлере, по тому же принципу, что в CAIRN. Добавить второго человека позже
будет стоить экранов, а не миграции данных.

## 4. Вычисляемые величины

Ничего из перечисленного не хранится.

- **Прогресс навыка** — сумма `points_awarded` по записям его трекеров,
  отнесённая к `target_points`.
- **Прогноз навыка** — темп за последние 14 дней, продлённый до конца
  периода: «при текущем темпе — 240 из 300».
- **Серия трекера** считается по неделям, потому что цель недельная. Неделя
  зачтена, если записей в ней не меньше `weekly_target`. Текущая серия — число
  подряд зачтённых завершённых недель. Текущая неделя показывается отдельно
  («2 из 3») и серию не рвёт, пока не кончилась: иначе каждый понедельник
  обнулял бы серию.
- **Процент выполнения за период** — записи, отнесённые к сумме недельных
  целей за недели периода.
- **Доля закрытых планов за период** — закрытые пункты ко всем.

**«Сегодня» определяет сервер** по зоне `HD_TIMEZONE` (по умолчанию
`Europe/Moscow`), а не браузер. Иначе запись в час ночи уехала бы на другую
дату, а статистика разошлась бы между телефоном и ноутбуком.

## 5. Стек

```
hundred-days/
  api/              Go 1.27: chi, pgx, sqlc, goose
  web/              Next 16: App Router, TanStack Query v5, shadcn/ui, Recharts
  openapi/          openapi.yaml — источник контракта
  docker/           Caddyfile, init для postgres
  scripts/          deploy.sh, backup.sh, restore.sh
  docker-compose.yml
```

**Next 16, а не 15.** В дизайне стояла пятнадцатая версия; к началу работы
текущей стабильной оказалась шестнадцатая, и ставить предыдущий мажор без
причины было бы хуже. Вместе с ней пришли Tailwind 4 (настройка в CSS, без
`tailwind.config.ts`) и React 19.

**Cache Components выключены.** Шестнадцатая версия предлагает режим, в
котором статическая оболочка страницы отрисовывается заранее, а динамика
подгружается за границами `<Suspense>`. Здесь статической оболочки нет
вовсе: каждый экран — данные одного человека за один день, и меняются они от
каждой галочки. При включённом режиме чтение `cookies()` вне `<Suspense>`
становится ошибкой сборки, и пришлось бы оборачивать в границы всё
приложение плюс держать `use cache: private` ради сессии — вся эта работа
ради ничего. Режим без Cache Components документирован и поддерживается,
`fetch` в нём по умолчанию не кэшируется, что здесь и требуется.

Хранилище — PostgreSQL 17. Развёртывание — Docker Compose. Язык интерфейса —
русский, без библиотеки локализации.

### 5.1. Контракт

`openapi/openapi.yaml` — единственный источник правды, обе стороны из него
производные:

- `oapi-codegen` порождает интерфейс сервера и типы в Go. Хендлер не
  скомпилируется, если разошёлся со спецификацией;
- `openapi-typescript` и `openapi-fetch` порождают типы и клиент в TypeScript.

Это замена `packages/shared` из CAIRN: в стыке Next и Go единого zod-контракта
не получается, и роль источника типов берёт OpenAPI. Сгенерированный код
коммитится, а CI проверяет, что перегенерация не даёт различий — иначе
расхождение спецификации и кода обнаружилось бы только в рантайме.

### 5.2. Доступ к данным

SQL пишется руками, `sqlc` порождает из него типизированные Go-функции. ORM
нет: запросов десятки, а агрегаты дашборда всё равно пишутся на SQL.

Миграции — `goose`, применяются при остановленных приложениях, как в CAIRN.

## 6. API

Всё под `/api`, сессия в cookie `HttpOnly`, `SameSite=Lax`, срок 30 дней со
скользящим продлением.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/auth/login` | вход по логину и паролю |
| `POST` | `/auth/logout` | выход |
| `GET` | `/auth/me` | текущий пользователь |
| `GET` | `/day?date=` | всё для страницы дня одним ответом |
| `PUT` | `/trackers/{id}/entries/{date}` | отметить выполнение, часы необязательны |
| `DELETE` | `/trackers/{id}/entries/{date}` | снять отметку |
| `PUT` | `/sleep/{date}` | записать сон |
| `DELETE` | `/sleep/{date}` | убрать запись сна |
| `POST` | `/day-plans` | добавить пункт |
| `PATCH` | `/day-plans/{id}` | правка текста, закрытие и открытие |
| `DELETE` | `/day-plans/{id}` | удалить пункт |
| `POST` | `/day-plans/carry-over?date=` | подтянуть незакрытые со вчера |
| CRUD | `/trackers` | реестр трекеров |
| CRUD | `/skills` | реестр навыков |
| `GET`, `PUT` | `/settings` | период и тумблер сна |
| `GET` | `/stats?from=&to=` | агрегаты дашборда |

`GET /day` отдаёт один ответ, а не шесть: это главный экран, он открывается
каждый день, и собранный из кусков он показывал бы шесть индикаторов загрузки
вместо одного.

Коды: `401` без сессии, `404` на чужую или несуществующую запись, `409` на
нарушение инварианта (`per_hour` у трекера без часов), `422` на негодные
данные.

## 7. Экраны

### 7.1. `/` — День

Главная. Открывается сразу на сегодня.

- Шапка: «Осталось 63 дня из 100» и полоса периода.
- Трекеры за дату: галочка, у `check_hours` — поле часов рядом. Под каждым —
  «2 из 3 на этой неделе».
- Планы на день: список с галочками. Кнопка «Подтянуть незакрытые со вчера»
  появляется только если такие пункты есть.
- Сон: лёг, встал, качество. Блок скрыт при выключенном тумблере.
- Короткий прогресс навыков: полосы к цели.
- Стрелки влево-вправо и календарь: любой день открывается и правится.

### 7.2. Остальные

- `/dashboard` — графики за выбранный период: 30 дней, 90 дней, весь период,
  всё время.
- `/trackers` — трекеры и навыки.
- `/settings` — период, тумблер сна, смена пароля.
- `/login`.

### 7.3. Правки

Все формы — в выезжающей панели, как в CAIRN: поля собираются в черновик и
уходят одной кнопкой «Сохранить», с предупреждением о несохранённом при
закрытии. Так правятся трекер, навык, настройки периода и текст пункта плана.

Исключение — сами галочки трекеров и планов: это одно нажатие, и панель для
него была бы издевательством. Они пишутся сразу, оптимистично, с откатом при
ошибке.

## 8. Графики

Recharts через `shadcn/ui charts`: он уже на Radix и Tailwind, токены темы
общие с остальным интерфейсом.

- **Теплокарта-календарь** по каждому трекеру — своя сетка на SVG, Recharts
  такого не даёт. Цвет по интенсивности. Дни сверх недельной цели не красятся
  провалом.
- **Прогресс навыков** — горизонтальные полосы к цели с меткой прогноза.
- **Часы по дням и неделям** — накопительные столбики с разбивкой по
  трекерам, переключатель гранулярности.
- **Серии и процент выполнения** — плитки сверху со спарклайнами.
- **Сон** — две линии (лёг и встал) по общей оси времени, полоса длительности
  под ними, качество точками.
- **Планы** — доля закрытых за период, отдельной метрикой. На поинты и навыки
  планы не влияют: иначе стёрлась бы граница между планом дня и трекером.

## 9. Тесты

Разработка по TDD: сначала падающий тест.

- **Go** — unit на вычисления: поинты, недельные серии, прогноз, длительность
  сна через полночь отдельным тестом. Интеграционные на хендлеры через
  `testcontainers-go` с настоящим PostgreSQL, как в CAIRN.
- **Web** — Vitest и React Testing Library: `ComponentName.test.tsx`,
  компонент до 100 строк, пропсы как `IProps` в `types.ts`, бизнес-логика в
  `utils/` с barrel-экспортом.

## 10. Развёртывание

Свой `docker-compose.yml`: `postgres`, `api`, `web`, `caddy` на
`${HD_HTTP_PORT:-8080}`. Своя база в своём томе, своё имя проекта compose,
свои имена образов — пересечений с CAIRN нет ни по портам, ни по томам, ни по
образам.

`scripts/deploy.sh` по образцу CAIRN, короче: проверки, копия базы, сборка,
остановка приложений, миграции, запуск. Рядом `backup.sh` и `restore.sh`.
GitHub Actions прогоняет тесты на push.

### 10.1. Доступ

На старте — `http://IP:8080`, без TLS. **Пока HTTPS не включён, пароль идёт по
открытому каналу** — это осознанная цена быстрого запуска, а не недоработка.

Поддомен с HTTPS — последняя задача плана, отдельная: блок в Caddyfile CAIRN,
проксирующий в `127.0.0.1:8080`. Это единственная строка связи между
системами. Свой Caddy с DNS-проверкой отвергнут: он дал бы тот же результат
ценой API-токена DNS-провайдера на сервере и сборки Caddy с плагином.

## 11. Вне объёма

- Напоминания и уведомления. Приложение не пишет первым.
- Исполнители, оценки, сроки у пунктов плана. План — список на день, не трекер
  задач.
- Вложенность планов и навыков.
- Публичные ссылки и чужой доступ к статистике.
- Мобильное приложение. Интерфейс отзывчивый, этого довольно.
